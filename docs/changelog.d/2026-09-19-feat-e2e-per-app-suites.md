### Changed
- **The e2e suite is now two packages, one per app:** `apps/e2e` is split into `apps/e2e-app` (projects `app` and `app-convex`, and the Convex harness) and `apps/e2e-www` (project `www`), with the shared free-port helper moved to a new `packages/e2e-kit`. New root scripts `pnpm test:e2e:app` and `pnpm test:e2e:www` run one suite; `pnpm test:e2e` still runs both. CI's e2e job is now a matrix with one job per suite, so they run in parallel and a failure names its app. *Why:* a www-only change no longer boots Vite and a Convex backend, and an agent in a worktree can test just the app it touched.

### Fixed
- **Several git worktrees can now run the e2e suites at once without colliding:** Reproduced first: with two worktrees whose Convex local deployments both recorded port 3210 (what any worktree provisioned while no backend is up records), the second worktree's run adopted the first's backend through `reuseExistingServer: true`, and only the admin-key identity guard stopped it wiping that database. Two Convex CLI behaviours are behind it, both confirmed in its 1.46.0 source: the recorded port is only a *suggestion* at boot (it silently moves to the next free one after Playwright has already handed the old one to the app), and before booting it waits for "its own" backend on the recorded port, recognising it by name, and every anonymous deployment is named `anonymous-agent`. So another worktree's backend reads as its own, and the CLI dies after five seconds. Now `apps/e2e-app` asks the OS for the backend's port pair on every run, like Vite's. `scripts/convex-local.mjs` repoints the recorded ports at that pair before booting and passes them as hard requirements (`--local-cloud-port`, which fails rather than drifts). The backend is started per run (`reuseExistingServer: false`) and stopped with SIGTERM. Each worktree keeps its own database under `packages/api/.convex/`, so only the process is per-run. Two runs of the *same* suite in the *same* checkout would share that database and `.next-e2e` and wipe each other's seed mid-run, so a new run lock (`.e2e-run.lock`, `packages/e2e-kit/src/run-lock.ts`) refuses the second one by name and takes over locks left by killed runs. Verified: all four runs (both suites in both worktrees, both recording 3210) at once passed 30/30 with no server processes left behind; an overlapping same-checkout run was refused while the first passed; a stale lock was taken over; and `packages/api/.env.local` still selects the cloud dev deployment. Documented in the new §1c of `docs/e2e-architecture.md`.
