## [4.4.0] - 2026-08-07

### Added
- **Playwright coverage for `apps/www`, including the first runtime tests for `motion`:** `apps/e2e` now runs one project per app — `app` against `apps/app` on `127.0.0.1:5173` and `www` against `apps/www` on `127.0.0.1:3100` — each with its own `webServer` and its own `baseURL`. Specs moved to `specs/<app>/` and page objects to `page-objects/<app>/`; the existing app suite was relocated unchanged. Eleven specs in `specs/www/landing.spec.ts` cover the hero, nav, footer, all six landing sections and the theme toggle; the two accessibility invariants described under *Fixed* below; the `MotionProvider` reduced-motion branch, which skips Lenis entirely and had no coverage at all; and — the part that did not exist before — four assertions on animation state: that below-the-fold content starts at `opacity: 0` and reaches `1` after scrolling, that the hero's `useScroll`/`useTransform` drift produces a transform, that the spring-driven reading-progress bar advances, and that every reveal on the page has fired by the foot of it. *Why:* `apps/www` had zero runtime coverage, which is exactly why the `motion` major below was held out of the routine sweep — a regression in any of those nine components would have left `typecheck`, `test`, `check` and `build` green. Three details are load-bearing and are documented in §9 of `docs/e2e-architecture.md`: Playwright's `toBeVisible()` ignores `opacity`, so a reveal that never fires still reads as visible and these assert computed opacity instead; scrolling must use `page.mouse.wheel`, because Lenis runs in root mode and a `window.scrollTo` fights it while a synthetic `WheelEvent` is untrusted and ignored; and a backgrounded tab throttles `requestAnimationFrame` and suppresses IntersectionObserver, which freezes every animation and imitates a broken library. `apps/e2e/tsconfig.json` gains the `DOM` lib, since `page.evaluate` callbacks are serialised and run in the browser. `reducedMotion` is set through `page.emulateMedia` rather than a `use` option — it is not a test-level option in Playwright 1.62. The full suite is 13 specs across both projects and runs in ~7s.
- **`data-testid` hooks on the `apps/www` landing surfaces:** `site-nav`, `reading-progress`, `hero-content`, `reveal`, `feature-card`, and one per section (`stack-marquee`, `showcase`, `built-with`, `cta`). *Why:* required by `AGENTS.md` §5, which asks for resilient data attributes over CSS classes. The animated wrappers have no accessible role or stable text of their own — several are `aria-hidden` decoration — so there was nothing else durable to select them by.
- **`apps/www/AGENTS.md` and `apps/www/CLAUDE.md`, generated by Next.js:** Both files are now tracked. *Why:* as of 16.3, `next dev` writes them next to the Next app — not the repo root — on every start; the generator is `next/dist/server/lib/generate-agent-files.js`, which is present in 16.3.0 and absent in 16.2.12, so this is new behaviour from the upgrade below and not something a config change introduced. `AGENTS.md` holds a managed `<!-- BEGIN:nextjs-agent-rules -->` block telling agents to read `node_modules/next/dist/docs/` before writing Next code; `CLAUDE.md` is the one-line `@AGENTS.md` import. Neither is gitignored, so they otherwise show up as untracked noise after any `pnpm dev`, and deleting them only makes the next `next dev` write them back — Next's own guidance is to commit the block, which is what we do. Note this repo now has two AGENTS/CLAUDE pairs: the root pair (where `CLAUDE.md` is a symlink to `AGENTS.md`) and this app-scoped pair (where `CLAUDE.md` is an `@AGENTS.md` import, Next's convention, not a symlink). They are additive rather than contradictory — the Next block only says to prefer version-matched packaged docs over training data, which is advice this upgrade independently vindicated (see the `@base-ui/react` note below). To opt out instead, set `agentRules: false` in `apps/www/next.config.ts`; to keep them untracked, `git rm --cached` both and add a `.gitignore` entry, which yields regenerated-and-ignored rather than gone.

### Changed

Next 16.3 is that flip — verified in the packaged source rather than inferred from release notes: `dist/esm/server/config-shared.js` defaults `useTypeScriptCli` to `false` in 16.2.12 and to `true` in 16.3.0. The option still exists and is still typed, so this is a default change, not a removal; the explicit setting was simply redundant, which is also why the `Experiments (use with caution): ✓ useTypeScriptCli` banner disappears from build output once Next stops seeing it as an override. A comment stays in `next.config.ts` recording the coupling that remains: **rolling `next` back below 16.3 requires rolling `typescript` back to 6.x as well, or restoring the flag** — TypeScript 7 ships without `lib/typescript.js`, the JS Compiler API that Next's default type-check path loads, so the pairing is atomic in both directions. Upgraded as its own step with `next` pinned to an exact `16.2.12` during the general sweep below, so 16.3 could not arrive as an unverified side effect of a caret range; the caret was restored afterwards. Verified with a clean `rm -rf .next` rebuild both before and after removing the flag — `tsc --noEmit` passing is not sufficient evidence here, since it enters the compiler by a different path than `next build` does and stayed green throughout the original 16.2 + TS 7 breakage.

- **`@base-ui/react` 1.6.0 → 1.7.0 taken deliberately, against an external recommendation to hold at 1.6.0:** An upgrade playbook written for a sibling repo pins this package to an exact 1.6.0 over a 1.7.0 `Select` regression: a `Select` whose value is set programmatically renders its placeholder instead of the selected item's label, and the trigger keeps `data-placeholder=""`. That report is credible — it reproduces only in a real browser, passing `tsc`, unit tests, Biome and `next build` — but it does not apply here, and the checks that establish that are worth recording. This repo imports exactly two things from Base UI, both `@base-ui/react/button` (`packages/ui/src/index.tsx` and `apps/www/components/ui/button.tsx`); there is no `Select` anywhere in `apps` or `packages`. `docs/react/components/button.md` shipped inside the package is byte-identical between 1.6.0 and 1.7.0. The `Button` stories in `packages/ui` run under `@vitest/browser-playwright` in real Chromium and pass. The companion 1.7.0 change — the trigger state attribute renamed `data-popup-open` → `data-pressed`, which appears in no release note and was found by diffing those packaged docs — is also inert here: `grep -r "popup-open"` over `apps` and `packages` returns nothing. **If a `Select` is ever added to this repo, re-read this entry before trusting 1.7.0**, and note that the only gate that catches the regression is a browser test.
- **`motion` 12.43.0 → 13.0.0, as its own change with a before/after measurement:** Held out of the dependency sweep above and done separately, because it is the only major in the set and `apps/www` — 72 `motion` usages across nine landing components, several scroll-linked through `useScroll`/`useTransform`/`useSpring`/`useMotionValue` — had no runtime coverage to catch a regression. *Why it is safe:* Motion 13's only breaking change for React is the removal of `@emotion/is-prop-valid` as an optional dependency, which affects CSS-in-JS users of Styled Components or Emotion. This repo has neither — no `styled-components`, `@emotion/*`, `isValidProp` or `motion.create` anywhere in `apps` or `packages` — so the change is inert here. *How it was verified:* rather than reasoning from the changelog, the landing page's animation state was measured on 12.43.0 and again on 13.0.0 with an identical scripted probe (hero transform, reading-progress `scaleX`, and the hidden/revealed count of every animated node, sampled at six scroll depths driven by real wheel events). **The two signatures are byte-identical**, down to `translateY(67.663px)` and `matrix(0.165346, …)`. The new `www` e2e suite above then locks that behaviour in permanently, so the next `motion` bump is an ordinary one. One measurement trap cost real time and is recorded in §9 of `docs/e2e-architecture.md`: an initial probe run in a backgrounded browser tab reported every animation frozen and every reveal unfired, which looked like a total regression and was purely an artifact of `requestAnimationFrame` throttling and suppressed IntersectionObserver in a hidden page.

### Removed
- **`docs/prd.md`:** Deleted. The template no longer needs a product requirements doc — `README.md` covers the stack and getting started, `AGENTS.md` covers the standards, `docs/e2e-architecture.md` covers the test suite, and this changelog carries the reasoning. Nothing in the repo linked to the PRD, so it had no readers and no mechanism keeping it honest: it went untouched from the initial commit (`ccb0c12`) through v4.3.1 and had drifted into describing a template that never existed — `apps/web` as a web-first "source of truth", an `apps/native` Expo + `react-native-webview` shell, Node 20, and a three-variable env contract. The last version of the file is recoverable from git at `12ff9aa:docs/prd.md` if a spec is ever wanted again, though it documents the pre-v4 layout and should be rewritten rather than restored. Four facts it recorded live nowhere else and are preserved here: (1) the planned Expo native shell was never built and is not the current direction, and the README's "Capacitor-ready" describes the shape of `apps/app`, not shipped tooling — Capacitor is not a dependency anywhere in the repo; (2) auth is off end to end — `apps/app` validates `VITE_CLERK_PUBLISHABLE_KEY` but never reads it, and `packages/api/convex/auth.config.ts` registers no provider; (3) `packages/api` has no tests, its `test` script is a placeholder `echo`, against `AGENTS.md` §5; (4) the PWA story is split and untested — the manifest is in `apps/www`, the service worker in `apps/app`, and neither surface has a verified offline path.

### Fixed
- **Links that open a new tab now say so:** All six `target="_blank"` links in `apps/www` — the hero and closing "GitHub" CTAs, the footer's "Cloudexible", both Instaclub text links in `built-with.tsx`, and the Instaclub screenshot frame — carry an "(opens in a new tab)" announcement. *Why:* sighted users learn the context switched because a new tab appears; screen reader users get no signal at all, and Back no longer returns them where they were (WCAG 3.2.5, Change on Request). Only the screenshot frame previously said it, and only incidentally — it is an image-only link that needed an `aria-label` for a name regardless, so the phrase happened to be bundled in. The other five announced nothing. A new `NewTabHint` component appends a visually hidden `sr-only` span rather than setting `aria-label` on the anchor: a label *replaces* the accessible name, so it must restate the visible text, then drifts silently when that text changes, and an imperfect restatement breaks WCAG 2.5.3 (Label in Name) for voice control. Appending composes with whatever the link already says. `sr-only` is `position: absolute`, so layout is untouched. The screenshot frame keeps its `aria-label` — it has no text to append to — with the wording aligned to match. Covered by an invariant spec that counts `a[target="_blank"]` and asserts every one of them has an accessible name ending in "(opens in a new tab)", rather than checking the links one by one: the point is to catch a *future* external link that skips the hint, since every current link already passes. **Verified to fail against a regression** — removing a single hint turns it red with `Expected: 6, Received: 5`, which also confirms the count is real rather than a vacuous `0 === 0`.
- **Button-styled links are announced as links again, with a single accessible name:** Two defects in the same two elements — the hero's "GitHub" CTA and the closing section's "Star on GitHub". (1) Both were `<Button render={<a href … />} />`. `apps/www/components/ui/button.tsx` passes `nativeButton={false}` whenever a `render` element is supplied, and Base UI's Button then enforces button semantics by stamping `role="button"` and `tabIndex` onto whatever it renders — an explicit `role` overrides the anchor's implicit link role, so assistive technology announced a navigating external link as a button. Base UI's own documentation is unambiguous: links "have their own semantics and should not be rendered as buttons through the `render` prop" (`node_modules/@base-ui/react/docs/react/components/button.md`). A new `ButtonLink` export renders a plain `<a>` carrying `buttonVariants` — the styling without the semantics; anchors already have link semantics and Enter-key activation from the browser, so nothing is lost. (2) `GithubIcon` set `role="img" aria-label="GitHub"` while sitting beside the visible words "GitHub" / "Star on GitHub", so the accessible name came out doubled — literally `"GitHub GitHub"`. It is now `aria-hidden="true"` and decorative, with `{...props}` still spread last so an icon-only usage can opt back in. *Why it went unnoticed:* nothing rendered wrong and nothing failed — the links worked, looked right and navigated correctly; only their announced role and name were wrong. It surfaced while writing the `www` suite, when `getByRole("link", { name: "GitHub" })` could not find an element plainly on the page. Both halves are now covered by a spec **verified to fail against the old code**: reverting the `ButtonLink` change makes the link locator resolve to 0 elements, and separately restoring the labelled icon does the same via the doubled name. Note `aria-hidden` must be the string `"true"` rather than the JSX boolean shorthand, or Biome's `a11y/noSvgWithoutTitle` flags the SVG as untitled.
- **The theme toggle no longer needs two clicks to do anything:** `apps/www/components/theme-toggle.tsx` now reads `resolvedTheme` instead of `theme`. *Why:* the layout sets `defaultTheme="system"`, so before any explicit choice `theme` is the literal string `"system"`, not `"light"` or `"dark"`. The handler was `setTheme(theme === "light" ? "dark" : "light")`, which on a light-preferring system evaluated `"system" === "light"` as false and set `"light"` — the theme already in effect. The `.dark` class did not change, nothing on screen moved, and the button looked broken until a second click. `resolvedTheme` is always the concrete theme actually applied, so the first click now always flips. Found by the new `www` e2e suite, not by inspection; the spec asserts the document theme differs after a single click.
- **`apps/www` dev resources are no longer blocked on `127.0.0.1`:** Added `"127.0.0.1"` and `"localhost"` to `allowedDevOrigins` in `apps/www/next.config.ts`, alongside the existing `*.turbostack.localhost`. *Why:* Next blocks `/_next` dev resources from any host not on that list, so serving the app on `127.0.0.1:3100` for the Playwright suite meant every JS chunk was refused — the page rendered its server HTML and never hydrated. Every client-side animation, and the theme toggle, were inert. This is the same failure mode recorded in v4.1.0 for the portless URL, and it is worth knowing that it presents as "the animation library is broken" rather than as a network error: seven of the nine new specs failed on it, and all but the two genuine defects above went green once the origin was allowed. Dev-only — Next ignores the setting in production builds.

## [4.3.1] - 2026-07-28

### Fixed
- **`pnpm typecheck` no longer depends on build output, unbreaking CI:** Added `apps/www/types/next-images.d.ts`, a tracked one-line `/// <reference types="next/image-types/global" />`. *Why:* `www#typecheck` failed in CI with `TS2307: Cannot find module '@/public/showcase/instaclub-dark.png'` while passing on every developer machine. `apps/www/tsconfig.json` includes `next-env.d.ts`, which is where Next puts that reference — but `next-env.d.ts` is generated by `next dev` / `next build` and is gitignored (`.gitignore:35`), so it does not exist in a fresh checkout. The alternative — reordering CI to build before typecheck — was rejected because it makes a fast check wait on a slow one and leaves `pnpm typecheck` still unable to stand alone in a clean tree.

## [4.3.0] - 2026-07-28

### Added
- **`docs/e2e-architecture.md`:** Reference for the `apps/e2e` Playwright suite — scope, web server lifecycle, POM discipline, DOM-reading technique, locator pitfalls, parallel safety against the shared Convex deployment, and a symptoms→causes table. Adapted from an external playbook written for a Next.js + Clerk + multi-tenant app; the sections that assumed that stack (two-tier seeding, namespaced tenant fixtures, seeder meta-test, Clerk `storageState` auth project, `ConvexHttpClient.setAdminAuth`) are listed in a "Deliberately out of scope" table with the trigger that would make each relevant, rather than carried as advice we don't follow. *Why:* the suite had one page object and one spec and no written intent, so there was nothing to check new specs against. Writing it down is what surfaced the five defects in §2 — a spec asserting against the wrong app, a teardown hang from an orphaned `vite` process, `reuseExistingServer` on outside CI, an untracked report directory, and no execution path at all — every one of which is **fixed in this same release**; see *Fixed* below, including which one turned out to be stale on inspection. §2 keeps them on record with their fixes rather than deleting them, because each is cheap to reintroduce and the reasoning is what prevents that.

### Changed
- **TypeScript 6 → 7 across the workspace, with `experimental.useTypeScriptCli` on `apps/www`:** Bumped the `typescript` catalog entry to `^7.0.2` — the Go-native compiler — and added `experimental: { useTypeScriptCli: true }` to `apps/www/next.config.ts`. *Why:* an earlier attempt at this upgrade was blocked by Next.js. TypeScript 7 ships without `lib/typescript.js`, the JS Compiler API that Next's built-in type-checking loads to detect the install; without it Next reported `typescript` as missing, tried to reinstall it, and crashed the build ([vercel/next.js#95400](https://github.com/vercel/next.js/issues/95400), [#95490](https://github.com/vercel/next.js/issues/95490)). The fix — invoking the `tsc` binary directly rather than the JS API — was backported to the 16.2 line in [#95831](https://github.com/vercel/next.js/pull/95831) and is available from 16.2.10, so it no longer requires 16.3. It is opt-in behind the flag above; the default path still uses the JS API, so the flag is load-bearing and must not be dropped until Next flips the default. Verified end to end: `typecheck`, `lint`, `test`, and `build` are green on all packages, and `next dev` serves a 200. The compiler is meaningfully faster — repo-wide `turbo typecheck` went 3.1s → 1.4s, and Next's own type-check step inside `next build` went 1552ms → 336ms. Note TS 7.0 has no stable programmatic compiler API (that lands in 7.1); nothing in this repo calls it, and Storybook's default `react-docgen` does not, but that is the constraint to check before adding TS-API-dependent tooling.
- **Dependency refresh across the workspace:** Catalog — `@biomejs/biome` 2.5.1→2.5.6, `@tailwindcss/postcss` + `tailwindcss` 4.3.2→4.3.3, `@types/node` 26.0.1→26.1.2, `convex` 1.42.1→1.42.3, `postcss` 8.5.16→8.5.24, `react` + `react-dom` 19.2.7→19.2.8, `storybook` 10.4.6→10.5.5. Per-package — `next` 16.2.9→16.2.12, `@clerk/nextjs` 7.5.10→7.6.2, `lucide-react` 1.22.0→1.27.0, `motion` 12.42.2→12.43.0, `posthog-js` 1.396.2→1.407.4, `vite` 8.1.0→8.1.5, `@vitejs/plugin-react-swc` 4.3.1→4.3.2, `vitest` + `@vitest/*` 4.1.9→4.1.10, `playwright` + `@playwright/test` 1.61.1→1.62.0, `@storybook/addon-{a11y,docs,vitest}` and `@storybook/react-vite` 10.4.6→10.5.5, `@commitlint/cli` 21.1.0→21.2.1, `@commitlint/config-conventional` 21.1.0→21.2.0, `lefthook` 2.1.9→2.1.10, `portless` 0.15.0→0.15.4, `turbo-ignore` 2.10.1→2.10.7. *Why:* routine maintenance; every one of these is a semver-compatible minor or patch and none required a code change. The `next` bump is also what makes the TypeScript 7 upgrade above possible, since the TS 7 backport landed in 16.2.10. `turbo` keeps its `latest` specifier but the lockfile was refreshed 2.10.1→2.10.7 via `pnpm update turbo`, since a floating `latest` does not re-resolve on plain `pnpm install`. `biome.json`'s `$schema` was repinned 2.5.0→2.5.6 via `biome migrate`, which is the whole of that migration — no rule or option changes. The `playwright` and `@playwright/test` bumps required no spec changes; the `apps/e2e` failures seen while verifying these upgrades predated them and are fixed separately in *Fixed* above.
- **Vercel preview deployments are off for every branch except `main`:** Added `git.deploymentEnabled` to both `apps/app/vercel.json` and `apps/www/vercel.json` with `{"**": false, "main": true}`. Vercel matches these keys with minimatch and deploys a branch if *at least one* matching rule is `true`, so `main` (matching both patterns) still deploys to production while every other ref — including PR branches and `dependabot/*` — creates no deployment at all. The `**` glob rather than `*` is deliberate: minimatch's `*` does not cross `/`, and this repo's branches are `feat/…`, `chore/…`, `dependabot/…`. *Why:* the workflow is trunk-based — work lands on `main` — so a preview build per push to a side branch burned build minutes and a Convex deploy for a URL nobody opened. This is stronger than the existing `ignoreCommand` (`turbo-ignore`), which only skips the *build* and still registers a deployment. To get a preview for a branch on purpose, run `vercel deploy` from the CLI, or temporarily add that branch (or a pattern) as `true` alongside the existing keys. Note the setting is read from the vercel.json in the pushed commit, so branches that predate this change keep deploying until they pick it up.

### Fixed
- **The `apps/e2e` Playwright suite is green and now actually runs in CI:** Closes all five defects recorded in §2 of `docs/e2e-architecture.md`. (1) `specs/home.spec.ts` and `page-objects/page.ts` asserted the heading `"The Modern Monorepo"`, which lives in `apps/www` — the app explicitly declared out of scope in §1 — while the config booted `apps/app`. They now assert what `apps/app` renders: `<h1>TurboStack</h1>`, the "Vite + React + Convex" tagline, and the message composer, split into two specs. The page-object getters were also made synchronous; a Playwright locator is a lazy selector, so the previous `await expect(await getHeading())` awaited nothing. (2) `webServer.command` went from `PORTLESS=0 pnpm --filter app dev` to `pnpm exec vite --port 5173 --strictPort` with `cwd: "../app"` — the old chain was pnpm → portless → vite, so Playwright killed the wrapper while vite survived reparented to PID 1 holding 5173, and teardown timed out *after* every test had passed. Vite is now a direct child; a full run exits on its own in ~2s and leaves the port free. (3) `reuseExistingServer` is `false` unconditionally rather than `!process.env.CI`: a reused dev server may carry a different `VITE_CONVEX_URL`, which makes a green run meaningless, and `--strictPort` now turns a busy port into a loud failure. (4) The reporter is `[["html", { open: "never" }], ["list"]]` — the default `open: "on-failure"` serves the report and blocks, which is what hung the first non-interactive run of this suite. (`playwright-report/` turned out to be gitignored already; that part of the defect list was stale.) (5) Added a root `test:e2e` script and a dedicated `e2e` job in `.github/workflows/ci.yml`, so the suite runs on every push and PR — previously `turbo test --filter=!e2e` plus a lint/typecheck/build-only workflow meant nothing ever executed it, which is exactly why (1) went unnoticed. *Why:* fixing the red spec without giving it an execution path would only have reset the clock on the same failure.
- **`e2e#test` is excluded from the turbo cache:** New task entry in `turbo.json` with `cache: false`, `dependsOn: []`, and `env: ["VITE_CONVEX_URL"]`. *Why:* `e2e` does not depend on `app` in the workspace graph, so apps/app's sources are not part of the task hash — a cached pass would be replayed intact after a UI regression, reporting green for a broken app. `dependsOn` is emptied because the suite drives Vite from source and needs no upstream build. The `env` declaration is required because Turbo 2 runs strict environment mode, and `apps/app` throws at startup without `VITE_CONVEX_URL`. CI passes a placeholder URL that is never connected to, the same trick the `www` build already uses; this constrains every spec to assert only on statically-rendered chrome, which is now recorded as a standing constraint in §2 of the e2e doc. Verified by running the suite with `.env.local` removed — green with the placeholder, red without any value at all, confirming the variable is load-bearing rather than incidentally satisfied.

## [4.2.0] - 2026-07-20

### Added
- **`.scratch/` local working directory:** New tracked folder holding only `README.md` and a self-scoped `.gitignore` (`*` with `!.gitignore` / `!README.md`), so the directory exists in every clone while everything a developer puts in it stays untracked. - **CI builds on every run:** Added a `Build` step to `.github/workflows/ci.yml` (job renamed `lint · typecheck` → `lint · typecheck · build`). *Why:* `typecheck` alone can pass while the build is broken — `tsc` is a standalone binary, but Next drives the TypeScript compiler API programmatically, so a compiler that fails to load leaves `typecheck` green and breaks `next build`. Verified by A/B in a clean worktree: with the catalog temporarily set to `typescript@7.0.2`, `pnpm typecheck` exits 0 while `pnpm build` exits 1 (`The "id" argument must be of type string. Received undefined`). The step sets `NEXT_PUBLIC_CONVEX_URL` to a placeholder — `apps/www` validates env at build time and requires a well-formed URL, but only the shape matters since prerendering never connects. - **`typecheck` for `apps/e2e`:** Added `apps/e2e/tsconfig.json` (extending `@repo/config/base.json`, with explicit `"types": ["node"]` for `process.env` in `playwright.config.ts`) and a `typecheck` script, plus the missing `@repo/config` dev dependency. *Why:* the package had real TypeScript (`playwright.config.ts`, `specs/`, `page-objects/`) and a `typescript` dependency but no tsconfig at all, so Turbo had nothing to run and the whole package went unchecked. `pnpm typecheck` now covers 6 packages instead of 5; the existing sources pass clean with no errors to triage.

### Removed
- **Redundant Storybook Vitest setup:** Removed `packages/ui/.storybook/vitest.setup.ts` and its `setupFiles` reference. `@storybook/addon-vitest` applies preview annotations automatically since Storybook 10.3, so the manual `setProjectAnnotations` call only emitted a warning. a11y enforcement is unaffected (verified: a violating story still fails the test run).

### Fixed
- **`packages/config` no longer bypasses the TypeScript catalog:** Dropped the `typescript: "latest"` dev dependency from `packages/config`. *Why:* every other package uses `typescript: "catalog:"` (pinned `^6.0.3`, which cannot reach 7), but `packages/config` pinned `latest` — and because `latest` always "satisfies", Dependabot never opens a PR for it. The lockfile happened to hold it at `6.0.3`, so it was latent rather than live, but any lockfile regeneration or `pnpm update` would have silently resolved it to 7.x with no review. The package is JSON-only (it ships `base.json`, `nextjs.json`, `react-library.json`, has no scripts and zero `.ts` source), so it never invoked `tsc` and the dependency was dead weight — dropping it is preferable to aligning it to the catalog. TypeScript 7 remains unadoptable regardless: it is the native port and no longer ships the JS compiler API that Next needs, and both `convex-helpers` (peer `^5.5 || ^6.0.0`) and `tsconfck` (`^5.0.0`) explicitly exclude it.
- **`setup:envs` no longer reports success when it does nothing:** `scripts/setup.mjs` now threads a found-count through its recursion and exits 1 with an error when zero `.env.example` templates are found, instead of printing `✨ Setup complete!` and exiting 0. *Why:* purely defensive — the templates in this repo are named correctly and the script works, but the silent-success-on-zero flaw is what hid the same bug for months in a downstream app whose template was misnamed. Idempotency is unchanged: re-running with an existing `.env.local` still skips without overwriting and exits 0 (both paths tested).
- **Convex deploy no longer fails on missing `CLERK_JWT_ISSUER_DOMAIN`:** `packages/api/convex/auth.config.ts` now hardcodes `providers: []` and no longer references `process.env.CLERK_JWT_ISSUER_DOMAIN`. The [3.0.2] "Clerk truly optional" change did **not** actually fix the deploy failure — Convex requires every env var *referenced* by the auth config to be set on the target deployment, regardless of runtime `if`/ternary guards, so the bare `process.env.CLERK_JWT_ISSUER_DOMAIN` read still failed `convex deploy` on any deployment without the var (e.g. Vercel preview builds, including Dependabot PRs). Removing the reference makes deploys succeed everywhere. *Trade-off:* backend auth is now off unless you re-add the provider and set the env var — matching the app layer, which already ships with Clerk bypassed.
